Threadline 38/40 · Excellent

16 actors · 32 flows · 8 views. Passes the 36/40 Excellent threshold.

Outbound (repo threadline) is a private, owner-only outbound sales tool hosted as a Next.js app on Vercel, with a Postgres CRM on AWS RDS. Nothing is sent automatically. The owner clicks Send on the Today screen, and a server action (gated by assertOwner) calls sendMessage in lib/engine.ts. sendMessage first claims the draft row in Postgres so a double click sends only once, then checks the stage, 24h limits, earlier replies and whether the owner is already in touch (if the in-touch lookup fails, nothing is sent). The send then goes one of three ways: - **Email:** sent through the Gmail API, threaded with earlier messages. - **LinkedIn:** queued as a run on a self-run Fly Chromium worker. The worker reaches LinkedIn through a Tailscale exit node on the owner's home network so LinkedIn sees a home IP. Outbound polls the run for up to 75s; if it hasn't finished, the next refresh resolves it. - **X:** has no API. The UI opens a prefilled DM, the owner sends it by hand inside X, and Send only records it. Separately, Vercel Cron (daily) and a Fly scheduled machine (hourly) call /api/cron with CRON_SECRET. That runs refresh(), which: - reads Gmail for replies and bounces; - asks the worker to read the LinkedIn inbox and recent posts; - uses OpenRouter LLMs to score fit, write drafts and label replies; - sources prospects from Apollo, Exa, YC and company sites; - writes CRM updates, drafts and runtime health back to Postgres. It never sends. On the owner's laptop, the scout CLI uses the owner's own gh, yc and bird (X) logins and POSTs what it finds to /api/import with a bearer token; that route resolves the project and persona and ingests the results. Gmail is connected through a Google OAuth callback that stores sealed tokens. LinkedIn sign-in happens inside the worker's browser, with the Settings page polling a screen-frame proxy.

Offstage 37/40 · Excellent

14 actors · 24 flows · 8 views. Passes the 36/40 Excellent threshold.

offstage has two parts. (1) A local tool: the offstage CLI/MCP looks at a command and either runs it in place (headless lane), in a Docker container with an Xvfb display (container lane), or, through a session adapter over a Unix socket, in a Swift sessiond running in a second logged-in macOS account on the same Mac (session lane). No lane ever falls back to the real screen. (2) offstage cloud: the CLI, a customer SDK and a React console all call one Hono control-plane API on a single Fly machine. Its state lives in memory and is snapshotted to a /data JSON file every 2 s, so a crash can lose up to 2 s. Fleet Macs have no inbound ports. A fleetd process in the operator account long-polls the plane (≤25 s) for tasks and sandbox ops, then runs them inside per-slot user accounts (separate uids on the same kernel and disk) via sessiond or sudo -u, and reports logs, exit status and artifacts back. Claims that aren't acked within 20 s are requeued, up to 3 attempts, and dirty slots are recreated before their next claim. Computer-use agent runs launch a GUI agent in a slot. The agent sends its model calls to the plane with a short-lived run token, and the plane forwards them to Anthropic using the customer's key, which never reaches the slot. For GitHub Actions, a workflow_job webhook makes the plane mint a JIT runner config. fleetd claims it, and the runner reports directly to GitHub. Console users sign in with Clerk (GitHub/Google), and the plane verifies each token server-side (502 if Clerk is unreachable, 401 if the token is bad).

Libra 38/40 · Excellent

16 actors · 27 flows · 7 views. Passes the 36/40 Excellent threshold.

Libra is mostly one Node/Hono process, libra-api on Fly, with an in-process priority scheduler and a SQLite source-of-truth database on its volume. Four kinds of client reach it: the Vercel dashboard, the customer's Claude plugin and CLI (MCP), GitHub webhooks and Slack events. (A) When a PR webhook arrives, the API records a gate audit and a run row in SQLite and starts a run-once Fly microVM. The VM fetches the base and head revisions from GitHub, replays traffic with no LLM and no customer credentials, and calls back with HMAC-signed evidence. The API then posts an advisory Check Run and line comments. (B) Customer OTLP spans are written synchronously to the libra-clickhouse app; if ClickHouse doesn't acknowledge the insert, the exporter gets a 503 and retries. Scheduler jobs reduce spans into incident_candidates in SQLite. Scout then claims a candidate, pulls customer AWS evidence, asks OpenAI for a verdict, records a signal_incident page claim and posts to Slack through the gated sendSlack path. If the Slack post fails, the claim is rolled back so it can retry. (P) The scheduler also polls PostHog with HogQL and stores triage jobs, findings and candidates. (C) A signed Slack thread reply becomes a durable general_question job. In production the in-process stateless responder answers it through the OpenAI Responses API; an alternate Codex worker can instead lease the job, using only scoped tools. Either way exactly one terminal reply is posted. (L) Libra Logs is a separate card-gated server with its own keys and ClickHouse, and it does not feed core PR review.
