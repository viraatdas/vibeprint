Latest rubric evidence
purpose4/4Every view opens with a one-line question title ('How does offstage execute a command away from your screen?', 'How does a fleet box claim a task, run it in a slot, and wipe it?', etc.), an audience line ('Engineers onboarding to offstage and offstage cloud') and a scope sentence that says what is left to sibling views. The level of detail (routes, timeouts, uids) suits that audience. The one blemish is the app header, which shows a random canvas id ('vp-offstage-detailed-SCyg6I') instead of a set title.
abstraction3/4View 1 is a context view and views 2–7 are zoom-ins, and the boxes are mostly at component level. Two things are stray. View 2 draws 'Headless lane' and 'Xvfb container lane' as peer participants of 'Session lane: sessiond', but the first two are code running inside the CLI process (view 3's subtitle admits this for the session client), while sessiond is a separate daemon in another account. The router, which is the component offstage exists for, is folded into the CLI box text ('Routes local lanes'). Sessiond is a box in view 2 but only an arrow-label word ('sessiond op') in views 5 and 6.
focus3/4Views are tightly scoped, and the omissions are stated ('result persistence is in the next view', 'helper display is covered in the local execution view'). Unstated gaps: (1) view 2 never shows what sends a command to which lane (no --headed, xcodebuild, simctl or open -a triggers), and the refusal exists only as note text; (2) view 1's notes say 'the CLI also offers sandbox tools', but the CLI is not drawn there, although view 4 draws it as a cloud client; (3) view 7 mentions billing and email verification, but no billing or mail provider appears anywhere (the code uses Stripe and api.resend.com).
flow4/4Every arrow I could see is labelled with protocol, payload and response, plus sync or local: 'B2 HTTPS long-poll /claim ≤25 s → work or 204 (sync)', 'C4 HTTPS /v1/model/messages with run token (sync)'. The legend fixes one meaning (caller → recipient, response included). Step numbers A1–A3, B1–B5, C1–C6 and D1–D4 give an order across views. Minor problems: in view 4, B1 sits below both C1 arrows in a top-down timeline, which implies an order that doesn't exist; and the 'B3/C3' and 'B5/C6' shared-step codes take decoding.
boundaries3/4Views 2–7 draw labelled containers that state ownership and deployment: 'Self-hosted Mac', 'Fly-managed: one machine (sjc) + offstage_data volume', 'Managed external providers; outside offstage trust boundary', 'Same Studio A Mac; separate customer uids'. Deductions: view 1, the overview, has no containers at all, only subtitle tags under each box. 'Fleet Mac: operator uid' and 'Fleet Mac: slot uids' are side-by-side siblings with no enclosing Studio A machine boundary. The same goes for the three regions on the developer's Mac ('Same machine' is text only). The network boundary (tailnet, pf LAN guard) appears only in notes. Containers and components are both pale or bold versions of the same red.
layout3/4No edge crosses another edge in any view. Each view has one direction: left to right in view 1, top-down timelines in views 2–7. Spacing is even and text is readable at 1194×834. Deductions: the notes panel takes about 195 of 834 px (y≈560–755), so the drawing gets a band about 400 px tall. Views 5 and 6 shrink to roughly 11 px box text while leaving about 150 px of empty margin at the right. Lifelines stop abruptly at the panel. Arrow labels run across intermediate lifelines (view 4 C1 across the CLI line at x≈495, view 6 C4 and C5 across the runner line at x≈515, view 7 D1 across the plane line). In view 1, Fleet runner sits in the left column with the customer clients, so it reads as one more customer rather than the execution side. Selector titles are cut off ('1/7 · How do cloud clients reach fleet …').
notation3/4There is a legend on every view: caller → recipient, headers = boundaries, faint guides = actors, cylinders = stores, solid = sync request, dotted = local I/O, equal stages = alternatives, unnumbered = independent. Line style and shape apply it consistently, which gives signals that don't depend on colour (cylinders for Run directory and Fly volume, dotted lines for local I/O). Deductions: the legend is generic (view 1 lists headers, guides and cylinders it doesn't contain). The flow letters (A = local, B = task, C = sandbox/agent, D = console) are never in the legend; each is defined only in its own view's subtitle, so view 5's 'B2–B5 … C3/C6' is opaque if you arrive from the selector. 'External' is signalled by text alone. Single-colour red ink flattens the hierarchy.
operations4/4Failure behaviour is explicit, with source paths given: the Fly plane on one machine as a single point of failure; acked writes held in memory with a snapshot every 2 s plus on SIGTERM, so a crash can lose about 2 s; claim long-poll ≤25 s returning 204; unstarted 20 s → requeue, max 3 tries; a box silent for 2 min fails its running task without rerunning it; heartbeat every 15 s delivers cancels; '409 = cancelled'; the LAN guard fails closed; reset before the next claim; no fallback to your display ('exit 69'); refusal on every lane; result.json writes can fail; op answers resent with backoff; the API key stays on the plane, with model, step and max_tokens checks. It is nearly all in the notes text rather than marked on the drawn components, and capacity (one Studio, offstage0–7) is only implied.
freshness3/4Each view has a footer: 'Source review 2026-11-05 · 57eeabc + local edits · Owner: Viaat Das (package.json author) · Live runtime NOT verified'. I spot-checked about 20 names and numbers against the code and they match: MAX_POLL_MS 25_000, CLAIM_ACK_MS 20_000, MAX_ATTEMPTS 3, BOX_LOST_MS 2 min, HEARTBEAT_MS 15_000, plane.json every 2 s plus SIGTERM, omt_ tokens, x-anthropic-api-key, /v1/model/messages, /v1/auth/clerk, Clerk JWKS, exit 69, DISPLAY dropped, --rm, fluxbox, stdin ignored, sudo -n -u. Capped at 3 because no runtime check was done.
comprehension3/4A newcomer can correctly retell the cloud path (SDK or console → Fly plane; the Studio runner long-polls, runs work as slot uids and resets them; agent model calls go through the plane to Anthropic) and the local path (CLI picks headless, Xvfb container or helper-session lane; artifacts go to a per-run directory). They cannot learn which commands go to which lane, how local offstage relates to the fleet (both use sessiond), or what billing and email depend on. Reading seven views plus dense notes, and decoding B3/C3, takes longer than two minutes. View 1's layout invites the misreading that the fleet is another client.
